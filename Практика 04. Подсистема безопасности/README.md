# Практика 4. Подсистема безопасности ИС

Что реализовано и где лежит в коде:

| Требование | Как сделано | Где |
|-----------|-------------|-----|
| Хеширование паролей | `generate_password_hash` из Werkzeug (scrypt + соль), в БД только хеш | `backend/security.py`, `backend/models.py` |
| Защита от SQL-инъекций | во всех запросах значения передаются параметрами `?`, строки SQL с данными пользователя не склеиваются | `backend/models.py`, `backend/db.py` |
| Разграничение прав | декоратор `login_required(role)`: гость получает 401 или редирект на вход, участник на админские страницы получает 403 | `backend/security.py` |
| Проверка данных на сервере и клиенте | на сервере `validators.py`, на клиенте `auth.js` и `request.js` (проверяются одни и те же правила) | `backend/validators.py`, `frontend/static/js` |
| Защита сессий и cookies | cookie `conf_session` с флагами HttpOnly и SameSite=Lax, срок жизни 30 минут, при входе сессия пересоздаётся (защита от фиксации сессии) | `app.py`, `backend/routes/auth.py` |
| CSRF | у каждого POST должен быть заголовок `X-CSRF-Token`, токен лежит в сессии | `backend/security.py` |
| Вывод данных | шаблоны Jinja экранируют HTML, в JS текст вставляется через `textContent` | `frontend/` |
| Заголовки | Content-Security-Policy, X-Frame-Options, X-Content-Type-Options | `app.py` |

Флаг Secure у cookie включается переменной `COOKIE_SECURE=1`, когда сайт будет работать по https. Локально без https он не нужен.

## Проверка

Написал 9 автотестов (`tests/test_security.py`). Они проверяют:

- пароль в БД хранится не в открытом виде;
- попытки инъекции в логин не пускают, таблица `user` остаётся на месте;
- гость не попадает на страницы участника и админа;
- участник получает 403 на админку, админ не может создавать заявки;
- POST без CSRF-токена отклоняется;
- у cookie есть HttpOnly и SameSite=Lax;
- сессия умирает через 31 минуту;
- `<script>` в отзыве выводится как текст.
