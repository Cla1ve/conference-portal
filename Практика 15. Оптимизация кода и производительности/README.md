## 2. Минификация CSS и JS

Скрипт `tools/build_static.py` (пакеты `rcssmin` и `rjsmin`) собирает файлы `*.min.css` и `*.min.js` в `frontend/static/dist/`. Исходники остаются как есть, их удобно читать и править.

Шаблоны теперь берут адреса через функцию `asset()` в `app.py`:
- если есть min-файл и он не старее исходника, отдаёт его;
- если исходник правили после сборки, отдаёт исходник (чтобы не показать устаревший код);
- добавляет `?v=` со временем изменения файла, чтобы браузер не держал старую версию;
- `USE_MIN=0` в окружении отключает подмену (удобно при отладке).

Результат (`05_минификация_css_и_js.png`): все файлы вместе 32 651 байт стали 23 547 байт, то есть на 28% меньше (по сжатию gzip на сервере ещё меньше: `style.css` 2,7 КБ). После подмены прогнал 12 автотестов Selenium, все прошли: сайт работает на минифицированных файлах.

## 3. Оптимизация запросов к БД

Написал `tools/explain_queries.py`. Он создаёт временную базу на 20 000 заявок, показывает план каждого запроса (`EXPLAIN QUERY PLAN`) и среднее время. Результат до индексов (`03_планы_запросов_до_индексов.png`) показал два места с полным перебором таблицы:

| Запрос | До | После | Что сделал |
|---|---|---|---|
| админ: фильтр по дате | `SCAN r`, 4,7 мс | `SEARCH e USING INDEX idx_event_date`, 0,2 мс | индекс `event(date)` |
| проверка перед удалением мероприятия (`WHERE event_id = ?`) | `SCAN request`, 0,8 мс | `COVERING INDEX idx_request_event`, 0,05 мс | индекс `request(event_id)` |
| заявки пользователя | индекс уже был | то же | без изменений |
| счётчики кабинета | индекс уже был | то же | заменил 3 запроса на 1 |

Индексы добавил отдельной миграцией `database/migrations/003_indexes.sql` (заодно составной индекс `event(room_id, date)` для фильтра по помещению и дате). Миграция применяется командой `python init_db.py` и записывается в `schema_version`.

Запрос "статус и помещение" остался около 15 мс на 20 000 заявок: SQLite выбирает индекс по статусу, и у статуса всего три значения, поэтому индекс почти не сужает выборку. Для портала с сотнями заявок это не проблема, поэтому оставил как есть. Поиск по названию (`LIKE '%текст%'`) индексом не ускорить, он перебирает таблицу, но на реальных объёмах быстро.
